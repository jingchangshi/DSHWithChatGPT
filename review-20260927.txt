## 2. 当前架构已经发生了一个非常关键的质变

你最初的核心问题是：

```text
DSH 在远程 Linux 上修改代码

但是

ChatGPT MCP 在 Windows 上读取代码
```

如果是这样，ChatGPT 的 independent review 从根本上就不可信。

现在最新两个 feature branch 已经基本解决了这个架构问题。

实际数据流已经变成：

```text
                    ChatGPT Web
               PLAN / REVIEW / Reason
                         │
                 @ DSH with ChatGPT
                         │
               Secure MCP Tunnel
                         │
                         ▼
               DSHWithChatGPT bridge
                         │
             WorkspaceRuntimeRegistry
                         │
              execution-world lease
              ┌──────────┴──────────┐
              │                     │
     ExecutionReadLease       ExecutionGitLease
              │                     │
              └──────────┬──────────┘
                         │
                  DSH provider world
                 ctx.fs / subprocess
                         │
              ┌──────────┴─────────┐
              │                    │
        Windows local         SSH remote Linux
```

这是目前代码中最有价值的一步。

DSHWithChatGPT 不再自己用 Host 的：

```text
fs.realpathSync()
fs.readFileSync()
execFile("git")
```

去假装访问 execution workspace。

最新生产路径改成了：

```ts
bindExecutionReadLease(...)
bindExecutionGitLease(...)
```

而真正执行这些能力的是 DSH。

所以架构现在已经接近：

> **Data plane follows execution world.**

这是整个方案是否成立的核心。

## 4. Git review data plane 也已经走到了正确方向

# 13. managed tunnel ownership 还有一个真实并发漏洞

这是我认为当前源码里值得优先修的一个具体问题。

现在还是：

```ts
const activeTasks = new Map(...)
```

用它阻止另外一个 workspace 抢占 managed tunnel。

问题是：

### 首轮 PLAN 时

执行：

```text
chatgpt_plan
→ ensureRuntime()
→ send INIT
→ await PLAN
→ activeTasks.set(...)
```

也就是说，**等待 PLAN 的整个期间 activeTasks 还没有记录该 task**。

这时另一个 workspace 如果调用：

```text
chatgpt_status
chatgpt_doctor
chatgpt_plan
```

理论上可以进入 `ensureRuntime()` 并重新 bind tunnel。

### Restart 后

durable task 还在：

```text
awaiting-plan
planned
awaiting-review
```

但：

```text
activeTasks = new Map()
```

重新为空。

只有 `chatgpt_reconnect` 以后才重新 set。

所以现在：

```text
durable task authority
```

和：

```text
managed tunnel ownership authority
```

仍没有完全统一。

最终 tunnel owner 应来自：

```text
durable active collaboration
+
current runtime binding generation
```

而不是 process-local Map。

这是相对小的问题，但到了最终 autonomous runtime 阶段值得解决。

```text

durable state
workspace identity
execution-world

Browser Harness
```

核心方向没有必要推倒重来。

**完成度已经比较高。**

大量：

```text
unit test
integration test
provider lifecycle test
real Browser Harness test
real SSH test
real Web process test
```

都已经存在。

### 第三层：产品闭环

**这是当前真正落后的部分。**

缺的是一条真正的：

```text
Windows DSH
→ real ChatGPT
→ real App
→ real Secure MCP Tunnel
→ real execution workspace
→ PLAN

→ REVIEW
→ fix PLAN
→ REVIEW

```

再加一条：

```text

→ SSH
→ Linux repo
→ same data plane
→ same execution plane
→ ChatGPT independent review
```

只要这两条真正打通，你的项目性质就会从：

> “架构完整的 C2C prototype”

变成：

> “实际可用于日常开发的 ChatGPT-guided DSH runtime”。

## 20. 接下来不应该继续大规模加新抽象

从当前源码看，我不建议再继续扩：

```text
更多 protocol state
更多 workspace abstraction
更多 SSH abstraction
更多 browser interface
```

下一轮工作的主线应该收敛到几个非常具体的问题：

```text
1. 真 ChatGPT C2C E2E
2. native Windows → Linux SSH E2E
3. execution_output + 通用 evidence
4. durable tunnel ownership
5. HANDOFF
6. ControlPlaneBrowser / ExecutionBrowser 隔离
7. matched release/package
8. 文档/model neutrality
```

其中 **1 是当前最大的 go/no-go gate**。在真实 ChatGPT App 能通过 Tunnel 读到 execution-world workspace，并完成一次 `PLAN → EXECUTE → REVIEW → DONE` 之前，不值得再扩大底层架构。

从源码层面看，你现在的方向是正确的，而且最近 `feat/complete-c2c-runtime` 的变化已经解决了此前最危险的设计问题——**ChatGPT review 与 DSH execution 不再天然属于两个不同的文件系统世界**。当前主要问题已经从“架构是否成立”转成“能否把这套架构真正完整运行并证明”。
