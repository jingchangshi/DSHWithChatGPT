# 二、本轮新增的最高优先级目标：避免“局部正确、整体腐化”

近期代码演进已经暴露一种重要工程风险：

模型能够不断产生局部正确、测试通过、安全性较好的 patch，但这些 patch 持续沉积后，可能把系统推向：

- 隐式状态机不断增厚
- mutable flags 增加
- recovery special case 增加
- 相同 lifecycle transaction 重复实现
- fixture / diagnostic infrastructure 持续膨胀
- 文档历史状态不断 prepend
- 模型每次需要理解越来越多历史上下文
- 每轮开发成本越来越高

因此，本轮开发必须把：

`correctness`

和

`complexity convergence`

同时作为一等目标。

禁止只因为 tests green 就认为工程完成。

# 五、增加 Architecture Debt Trigger

从现在开始，每一次想修改 production source 前，都必须执行以下检查。

如果任意一项为 YES：

1. 同一机制最近已经被 patch ≥ 3 次
2. 本次需要新增 mutable boolean / state field
3. 本次需要新增 recovery special case
4. 本次需要增加新的 “if X then retry/reload/recover”
5. 本次需要复制一个已经存在的 lifecycle transaction
6. 本次 fixture 必须知道更多 production private state 才能工作
7. 新 failure 无法映射到已有 invariant / state
8. Reviewer 的建议本质上是“再加一个 branch”
9. 同一函数已经承担多个不同生命周期阶段
10. 为修当前问题必须修改多个层的隐式约定

则：

**禁止立即继续局部 patch。**

必须先通过 codex-with-chatgpt 发起：

`ARCHITECTURE_CONSOLIDATION_REVIEW`

让 ChatGPT 基于真实源码回答：

- 当前 invariant 是什么
- 当前 mechanism 是什么
- failure 属于哪一个 invariant
- 是否是缺失 state
- 是否是已有 state transition bug
- 是否应该抽取 state machine / transaction
- 哪些旧逻辑可以被删除
- 怎样重构才能减少而不是增加状态数量
- 如何用现有测试证明行为等价

没有独立架构方案，不要自行发明大型抽象。

# 七、统一 Sidecar Handoff Transaction

独立检查当前是否存在两套或更多近似流程：

bootstrap recovery：

create replacement
→ close source
→ start replacement
→ health
→ semantic readiness
→ reconcile
→ commit
→ retire source
→ rollback on failure

App-proof recovery：

create replacement
→ close source
→ start replacement
→ health
→ recover
→ resume original wait
→ proof
→ commit
→ retire source
→ rollback on failure

如果独立 review 确认确实是同一 transaction：

抽取一个内部：

`OwnedSidecarHandoff`

或等价机制。

状态建议体现类似：

PREPARED
→ REPLACEMENT_CREATED
→ SOURCE_RELEASED
→ REPLACEMENT_STARTED
→ TRANSPORT_READY
→ SEMANTIC_READY
→ PROVED
→ COMMITTED

失败：

→ ROLLED_BACK / UNCERTAIN

不同 caller 只提供：

- readiness callback
- proof/reconcile callback
- commit callback

不要把 App-proof / bootstrap 产品语义硬编码进通用 handoff transaction。

必须保持：

- one replacement budget
- no resend
- original operation ID
- original absolute deadline
- exact source/replacement ownership
- commit only after proof
- rollback on failure
- source retirement only after commit
- unknown stays unknown

# 十六、执行顺序

现在开始，不要只输出计划后结束。

按以下顺序持续工作：

1. 获取两个 repo 当前真实状态。
2. 阅读当前 goal / target architecture / current status / latest evidence。
3. 通过 codex-with-chatgpt 发起一次独立 ARCHITECTURE + CURRENT CANDIDATE review。
4. 判断最新候选是：
   - 需要最小 source fix
   - 可以 freeze
   - 必须 architecture consolidation
5. 优先完成当前真实产品 gate，不要因为美化代码无条件推迟真实 E2E。
6. 一旦触发 Architecture Debt Trigger，停止继续堆 patch，进行 consolidation。
7. 每次重构必须减少或集中状态，而不是增加抽象数量。
8. 每次 production candidate 都执行：
   causal RED
   → focused
   → architecture/source review
   → native/adversarial
   → typecheck/build
   → one frozen full
   → package/profile association
   → push
   → exact-HEAD review
9. 然后进行一次真实 controlled exposure。
10. 持续推进直到最终产品闭环或者遇到真正需要用户操作的外部 blocker。

最重要的原则：

**Tests green 是必要条件，不是完成定义。**

**每个 failure 必须先属于一个 invariant 和 mechanism，而不是自动产生一个新的 branch。**

**优先删除和统一机制；只有不能由现有机制表达时才增加新的 state。**

**目标不是让当前 issue 关闭，而是让 PlannerBridge 在后续需求继续演化时仍然容易理解、验证和修改。**
